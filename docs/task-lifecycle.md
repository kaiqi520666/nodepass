# 任务状态与积分流转

整理日期：2026-11-07。状态：第一版设计草案；图片任务、独立 Worker、OSS 转存和冻结/结算/释放事务已实现，视频和素材输入仍未实现。

业务规则以[需求确认](requirements.md)为准，字段和约束见[数据库表结构](database-design.md)。本文说明内部状态，不直接定义对外 OpenAI 兼容响应；对外接口须单独做协议映射。

## 核心规则

1. 提交时冻结原报价积分；上游生成成功不等于本站成功。
2. 全部应交付结果转存至本站阿里云 OSS 并校验就绪后，本站成功与积分结算在同一数据库事务完成。
3. 明确失败释放冻结资金；超时、查询异常、下载失败、OSS 转存失败均不自动等同失败。
4. 超时后继续查询原任务，迟到成功自动走相同的转存、交付与结算流程。
5. 不盲目重复提交上游，不因重试产生重复生成或重复扣费。

## 三种状态分开记录

| 层次 | 字段 | 说明 |
| --- | --- | --- |
| 本站执行 | `tasks.status` | 本站当前在提交、等待、转存还是已完成 |
| 上游执行 | `tasks.upstream_status` | 适配器归一化的上游状态，不直接驱动资金变更 |
| 任务账务 | `tasks.billing_status` | 冻结、结算、释放、已结算退款 |

`timed_out_at` 和 `review_required` 是异常事实与核实标记，不再把它们排列组合成更多任务状态。临时错误记录在错误字段与审计中。

### 本站执行状态

| 状态 | 中文含义 | 允许的后台动作 | 正常账务状态 |
| --- | --- | --- | --- |
| `queued` | 已受理，待本站提交 | 领取执行租约，准备提交 | `held` |
| `submitting` | 正在向上游提交 | 当前领取者执行一次生成提交，保存受理结果 | `held` |
| `submission_unknown` | 无法确认提交是否受理 | 核实原提交，不自动重发 | `held` |
| `pending` | 上游已受理，等待执行 | 查询原上游任务 | `held` |
| `processing` | 上游生成中 | 查询原上游任务 | `held` |
| `transferring` | 上游已成功，结果待转存 | 恢复结果下载及 OSS 上传，不再生成 | `held` |
| `succeeded` | 本站结果已就绪并结算 | 按权限获取结果，不再执行生成与结算 | `settled` |
| `failed` | 已核实的明确失败 | 展示失败，不再生成 | `released` |

首期不增加取消、重生成、部分成功或部分退款状态。需要更改已结算账务时保留执行事实，使用独立资金动作与审计，不伪造执行失败。

### 允许的执行流转

```text
queued -> submitting -> pending -> processing -> transferring -> succeeded

submitting -> submission_unknown
submission_unknown -> 核实原任务后继续 pending / processing / transferring
submitting / pending -> transferring（上游直接完成时）

明确失败：按下表进入 failed，并在同一事务释放冻结积分
超时：只标记 timed_out_at，不沿箭头进入 failed
```

下表是执行流转的完整设计清单；重试同状态不列为新边。所有流转都需锁定任务并校验当前状态，非表内变更不能直接写入：

| 起点 | 允许终点 | 前提 |
| --- | --- | --- |
| `queued` | `submitting`, `failed` | 领取提交权；或在确认尚未调用上游时发现不可恢复的受理后错误 |
| `submitting` | `pending`, `processing`, `transferring`, `submission_unknown`, `failed` | 受理返回对应状态；受理不明；或有明确未受理、明确失败证据 |
| `submission_unknown` | `pending`, `processing`, `transferring`, `failed` | 核实为原提交的上游任务或取得明确失败、未受理证据；不得凭猜测新建任务 |
| `pending` | `processing`, `transferring`, `failed` | 原任务查询给出对应确定结果 |
| `processing` | `transferring`, `failed` | 原任务完成或明确失败 |
| `transferring` | `succeeded` | 全部预期输出在本站 OSS 就绪并完成同事务结算 |
| `succeeded` | 无 | 执行终态，异常结果另记审计并核实 |
| `failed` | 无 | 执行终态，异常迟到结果不自动重新收费 |

可能直接拿到完成结果，所以允许跳过等待、处理中状态。适配器只转换明确含义，不能把未知字符串归为失败。已有 `processing` 不被迟到的排队响应退回 `pending`；进入转存后不被较旧查询结果降级。

`transferring` 出现源地址失效、上传错误时保留此状态并安排恢复、必要时标记人工核实。永久无法交付的关闭和资金处理仍待确认，不擅自添加自动失败边。

## 超时和人工核实

- 受理时保存 `deadline_at`；达到阈值仍未完成时只写一次 `timed_out_at`，不能释放积分或清空原上游 ID。
- 活跃任务的界面可主显示“超时”，同时显示实际阶段，如“上游处理中”或“结果转存中”。
- 完成后显示“成功”或“失败”，保留“曾超时”记录；不能永远用超时覆盖最终结果。
- 有上游 ID 时继续查询原供应商原任务；查询失败按安排重试，不提交第二次生成。
- 没有上游 ID 的 `submission_unknown` 无法凭空查询。标记待核实，利用供应商提供的原请求查询能力或管理员证据恢复关联；无可靠能力时等待核实，不假装能自动恢复。
- 超时后的成功仍自动转存并结算，只要该任务账务仍为 `held`，不要求管理员逐笔批准。
- 管理员不能直接编辑状态或余额绕过检查。核实关联、确认失败等操作记录证据并调用相同业务服务。
- 长期查询退出、无法交付、人工关闭后收到相反终态的处理仍待确认。没有明确策略前，不按重试次数或天数自动关闭、退款或二次扣款。

## 账务状态及金额

### 资金动作

| 动作 | 原状态 → 新状态 | 可用余额变化 | 冻结余额变化 | 事件键示例 |
| --- | --- | --- | --- | --- |
| 兑换充值 | 不属于某任务 | `+A` | `0` | `code:<id>:redeem` |
| 提交冻结 | 新任务 → `held` | `-A` | `+A` | `task:<id>:freeze` |
| 成功结算 | `held` → `settled` | `0` | `-A` | `task:<id>:settle` |
| 失败释放 | `held` → `released` | `+A` | `-A` | `task:<id>:release` |
| 已结算退款 | `settled` → `refunded` | `+A` | `0` | `task:<id>:refund` |

`A` 为受理时保存的 `sale_amount`，不是执行当天的新价格。每一种动作只执行一次；结算与释放必须互斥。正常失败发生在冻结阶段，使用 `release`，不是既释放又退款。

已结算退款仅保留单次全额退款所需的账务表达，不代表已经确定管理员可任意退款的产品策略或新增退款页面。触发条件、证据与授权必须在开放入口前落实；不自动因超时退款，不增加部分退款规则。

任务处于六个活跃状态时必须为 `held`；普通成功为 `settled`，普通失败为 `released`。若已结算后按明确授权退款，可保持执行 `succeeded`，账务为 `refunded`，因为生成交付事实没有消失。禁止 `released -> settled` 或 `released -> refunded`。

### 舍入和示例

```text
图片 / 按条视频：quantity = 1
按秒视频：quantity = 用户提交且通过模型能力校验的指定秒数
sale_amount = 单价乘以数量，再按 ROUND_HALF_UP 保留四位小数
```

Python 算术示例使用字符串构造 `Decimal` 和足够的运算精度，不先用浮点数相乘。实际受理仍需按表字段精度校验范围。请求秒数不按实际视频时长重算，不另取整。

```python
from decimal import Decimal, ROUND_HALF_UP, localcontext

with localcontext() as context:
    context.prec = 64
    unit_price = Decimal("0.1235")
    quantity = Decimal("1.5")
    sale_amount = (unit_price * quantity).quantize(Decimal("0.0001"), rounding=ROUND_HALF_UP)
    assert sale_amount == Decimal("0.1853")
```

| 场景 | 受理前可用 / 冻结 | 冻结后可用 / 冻结 | 结算或释放后可用 / 冻结 |
| --- | --- | --- | --- |
| 售价 `0.1000`，成功 | `100.0000 / 0.0000` | `99.9000 / 0.1000` | `99.9000 / 0.0000` |
| 售价 `0.1000`，明确失败 | `100.0000 / 0.0000` | `99.9000 / 0.1000` | `100.0000 / 0.0000` |
| 售价 `0.1000`，超时未终结 | `100.0000 / 0.0000` | `99.9000 / 0.1000` | 不结算、不释放，保持冻结 |
| `0.1235` 积分/秒，请求 `1.5` 秒 | 金额 `0.18525` | 四舍五入冻结 `0.1853` | 成功仍结算 `0.1853` |

最后一项只验证算术，不表示任何上线模型支持 1.5 秒。成本价另外保留快照，不改变用户冻结金额；未知实际成本不写零，不用估算成本生成已实现利润。

## 事务与执行顺序

### 1. 受理与冻结

1. 校验认证、用户状态、模型上架、参数能力、图片单张、素材归属及有效价目。
2. 在数据库事务中取得一致的模型、供应商和价目配置，生成参数与价格快照。配置读取和更新必须避免混用不同版本，可先以模型行作为配置锁入口。
3. 若使用受理幂等键，同一用户同键同请求返回已有任务；不同请求拒绝复用。并发创建由唯一约束兜底，冲突事务回滚后读取已提交的原任务，不留下第二笔冻结。
4. 锁定积分账户，检查可用金额，创建 `queued / held` 任务、素材关联与冻结流水，更新可用及冻结余额，在同一事务提交。
5. 提交后才发送执行消息。发送失败不回滚已提交账务，由数据库恢复扫描补发 `queued` 任务。

不预建通用事务消息平台；数据库中的可恢复任务安排已经覆盖首期消息丢失场景。尚未提交的任务不能被 Worker 当成可执行任务。

### 2. 提交上游

1. Worker 短事务锁任务，确认 `queued / held`，领取带有效期的执行租约，改为 `submitting` 后提交事务。
2. 数据库事务外调用绑定的上游生成接口；不自动重试这个可能产生费用的 POST。
3. 锁任务保存原上游 ID、受理状态与后续安排，再转为 `pending`、`processing` 或 `transferring`。遇到明确拒绝才走失败释放。
4. 网络断开、响应无法解析、进程在提交中崩溃，无法证明上游未受理时进入 `submission_unknown`。过期的 `submitting` 也不能改回 `queued` 再生成一次。

租约不是上游幂等能力。数据库提交和上游 HTTP 调用无法组成一个本地原子事务，因此不能承诺远程“恰好一次”；这里用受理不明隔离风险。即使请求实际上尚未发出，只要无法可靠证明，也先核实。

### 3. 查询原任务

- 从任务原供应商绑定和上游 ID 查询，不从当前模型映射重新选择供应商。
- GET 网络异常、限流、服务器错误、单次 404 或未知状态保留任务，记录问题并安排重试；是否明确失败由适配器依据已核验协议判定。
- 查询成功更新上游状态；明确失败触发释放，上游成功时在同一事务固定全部预期输出槽位并进入 `transferring`，避免只持久化一部分结果。
- 执行租约到期可重新领取安全查询，但旧 Worker 写回须校验令牌和当前状态。已过期提交请求的迟到响应若带回原任务 ID，必须在锁内核对原请求关联后恢复，不能直接覆盖新状态。
- 持久化 `next_run_at`，启动后和周期性扫描补派到期任务；数据库中仍活跃的任务不能只靠 Redis 中的一条消息存活。

查询间隔、网络超时与安全重试退避可以配置；它们不是用户业务配额，也不能隐含“达到次数自动退款”的规则。

### 4. 转存结果

1. 持久化原结果来源和预期输出槽位，不使用临时内存作为唯一恢复依据。
2. 下载、类型检查、大小限制及 OSS 上传在数据库事务外执行；保留必要访问兼容设置，但不因下载错误重新生成。
3. 使用稳定的对象键，结合 SDK 校验和对象元信息确认转存完成。不能对所有上传模式假设 `ETag == MD5`。
4. 写入或复用对应输出素材，标记就绪，再尝试结算。源地址过期时可按上游支持的能力重新获取原任务结果地址，不能发新生成请求。
5. 转存失败继续 `transferring / held`，记录错误与恢复安排。不可恢复的关闭策略待确认。

上传成功而数据库写入前崩溃时，恢复流程核对已有对象归属和校验信息后补记，不能仅因存在同名对象就跳过校验。输入素材是否需要转存仍按上游要求，不受输出强制转存规则影响。

### 5. 成功结算

一个数据库事务内：

1. 按“任务 → 积分账户”的顺序加锁；校验 `transferring / held`。
2. 确认任务拥有非空、数量符合要求的完整输出关联，且全部本站 OSS 结果已校验为 `ready`。素材就绪状态一经用于交付，不允许其他路径并发回退或删除。
3. 账户冻结减少原 `sale_amount`，写唯一结算流水，将任务改为 `succeeded / settled` 并记录完成时间。
4. 提交事务后，查询与下载入口才将任务作为成功交付；不得在事务提交前先返回成功链接。

若任务已经结算，同一请求只返回既有结果。若已释放或状态矛盾则拒绝再次扣费，留待核实。OSS 对象本身不参与数据库事务，先存储、后结算。

### 6. 明确失败与释放

同样按“任务 → 积分账户”加锁：校验失败证据、允许的执行状态及 `held`，把原金额从冻结还给可用，写释放流水，并同事务改为 `failed / released`。

相同失败结果重复到达只返回已有记录；已结算任务不能再走释放。较旧响应或矛盾终态不能覆盖已完成交付，记录审计并核实。

### 7. 兑换充值

先锁兑换码再锁积分账户，检查未兑换；同事务写兑换人、兑换时间、账户可用增量和唯一充值流水。并发兑换只有一方成功；原兑换人网络重试可以返回原兑换记录，其他用户不能重复取得积分。

生成码需要高熵随机值，只存摘要；不增加有效期、禁用流程或可重复兑换次数。

### 8. 已结算退款

仅在有明确授权和依据时进入：按“任务 → 积分账户”加锁，校验 `settled`，向可用余额退回原金额、冻结不变，追加唯一退款流水并改为 `refunded`，与操作审计同事务提交。

不能修改或删除原结算流水，不能把 `released` 再退款，也不能拿新售价计算退款。该节说明数据安全边界，不自行开放尚未确定的业务入口。

## 恢复与幂等检查

| 中断或异常 | 恢复方式 | 禁止动作 |
| --- | --- | --- |
| 冻结已提交，队列消息丢失 | 扫描数据库，补派 `queued` | 再创建一份任务并冻结 |
| Worker 领取提交权前崩溃 | 仍是 `queued`，重新领取 | 根据同一消息生成新任务 |
| Worker 在 `submitting` 崩溃 | 核实是否受理，不能证明则 `submission_unknown` | 租约到期后自动重发生成 |
| 上游 ID 已保存，查询中断 | 按原 ID 恢复查询 | 用当前模型绑定改查其他供应商 |
| 查询临时错误或任务超时 | 保留冻结，继续原任务查询 | 自动按失败退款 |
| 上游成功，结果下载返回错误 | 恢复原结果下载或获取原任务结果地址 | 再次生成 |
| OSS 成功，数据库未写入就崩溃 | 校验稳定对象并补记输出素材 | 未校验就认定成功或重复收费 |
| 结算已提交，响应发送失败 | 返回已结算任务及本站结果 | 第二次结算 |
| 两个 Worker 同时尝试结算、释放 | 任务锁及资金状态使两者互斥 | 只依赖两个不同的流水唯一键 |
| 后台修改价格、供应商映射 | 旧任务仍用原绑定与金额快照 | 用新价结算旧任务 |
| 终态后收到矛盾结果 | 留审计与核实，不自动改账 | 推翻终态并再次扣款或退款 |

上述设计不提供跨供应商切换、自动重新生成、自动清理或业务并发配额。

## 实现后的验收用例

以下是必须补入业务测试的验收清单，不代表已经测试通过：

- `0.18525` 正向四舍五入得到 `0.1853`；价格和金额全程无二进制浮点。
- 按张、按条均取数量 1；按秒使用请求的合法秒数，实际结果时长不同也不改价。
- 不支持参数先拒绝，不能误命中默认价；精确价优先，缺价拒绝，配置修改不混用半套价目。
- 同一账户并发提交，冻结总额不能超过余额；同一受理幂等键不能冻结两次。
- 同码并发兑换、重复结算、重复释放和重复退款只发生一次；结算与释放竞争只能成功一个。
- 上游受理但响应丢失、提交进程崩溃，都不自动产生第二次生成。
- 超时不释放；迟到成功自动转存并只结算一次；查询异常不误判失败。
- 转存失败不返回成功、不结算；重启后复用原任务、输出槽位及经校验的本站对象。
- 无输出、仅参考图就绪、跨用户引用、源链接伪造或存储校验不通过均不能成功结算。
- 上游地址、能力、价格和 OSS 配置调整不损坏旧任务恢复与旧结果访问。
- 普通用户不能访问其他用户任务、素材或成本信息，不能调用管理核实与资金操作。
- 流水重放与账户余额一致，冻结总额等于 `held` 任务金额之和，原币估算不冒充已核验实际成本。

## 仍待确认

长期无法确认终态时何时停止查询、无法交付如何关闭、人工资金处置及关闭后出现相反结果的规则，仍见[待确认事项](requirements.md#待确认事项)。在确认前保持事实、冻结与核实记录，不预设自动退款或再次收费。
